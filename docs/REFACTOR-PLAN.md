# codex-wechat 整体重构计划

2026-11-02。计划稿，尚未实施；两侧源码均为设计输入，不以保留原模块为目标。

## 目标与边界

一个项目、一个权威源码库，同时考虑 Linux / Windows、Codex CLI / App 和 codex-deepseek。可以重写全部模块；保留用户需要的行为，不保留重复实现、临时工具或已经失效的兼容分支。

- 用户满意的旧提示、指令、短名和热设置作为展示基线。新增开发中的提示可以重做，先给紧凑预览。
- 代理启动器只处理代理并转交命令；不管理后台、端口、进程记录、微信或会话。
- 不复制 Codex 的认证、供应商请求、会话存储、模型配置和 Agent 执行器。
- 不迁移双系统间的 Agent 进程、待办、聊天游标或凭据。两边源码统一不等于运行状态同步。
- Python 仍作为主要实现语言；先不引入数据库、事件总线、插件框架或通用多 Agent 抽象。
- 本次不改变正在使用的服务，不因验证而结束桌面会话、删除写入锁或替换当前绑定。

## 目标结构

按下表划分职责，落地时才确定文件数量；不把每项职责机械拆成一个类或文件。

| 部分 | 负责 | 不负责 |
| --- | --- | --- |
| 应用层 | 启停编排、命令、设置、状态快照与展示 | 协议分帧、平台服务细节 |
| 微信层 | 登录/重绑、长轮询、发送、媒体协议与认证错误 | Codex 后台与会话 |
| 交付层 | 输入提交、steer/queue、输出分组、去重和恢复 | 模型执行、系统自启 |
| Codex 接入层 | 原生连接、会话/轮次/事件、审批/提问和能力核对 | 供应商客户端、代理策略 |
| 平台与部署层 | 原生服务、进程、路径、通知、二维码、安装与更新 | 重复一份业务流程 |

CLI、App、微信是同一 Codex 后台的客户端；codex-deepseek 保留自己的启动入口与身份环境，不演变成另一套微信桥。

代理启动器可转交原生命令或项目接入入口。项目入口只表达连接需求；后台发现、准备、就绪与所有权集中在运行管理组件。连接建立后，桥接关闭只释放自己拥有的连接和子进程。

## 实施顺序

### 1. 留存两侧成果，建立行为基线

- 从真实 Git 基线和 D 盘文件清单重建差异，核对文件内容，不整目录覆盖。
- 把 Windows 独有源码和原 CLI 导出的修正留存到可追溯提交；实验脚本与机器配置只作参考，不进入正式发行载荷。
- 记录需要保留的用户行为、已有数据格式和已知缺口。旧测试用于寻找约束，不能直接成为新设计的全部规格。
- 为重构使用独立分支/工作目录；不切换当前运行服务指向的源码。
- 明确源码归宿：建议使用独立项目私有库作为唯一开发源，cfg 管本机配置；不得把整个 cfg 当项目库推送。执行迁移前确认仓库归属。

交付：来源清单、行为清单及重构工作分支。此时不删除 D 盘目录。

### 2. 核对原生能力，决定接入与后台方案

- 核对两侧实际 CLI、App 内置 CLI、App 打包版本及 codex-deepseek 的启动约定。
- 对 CLI 查对应标签的公开源码、App Server 协议及本机 schema；对 App 查当前打包实现。公开协议、内部实现和实测事实分别记录，不泛称所有 App 实现都开源。
- 重点查 daemon / proxy / `--remote`、会话共享、事件与请求归属、启动参数和配置覆盖；确认原生机制能覆盖后才删除自管实现。
- 原生后台能满足时直接复用；若某平台的 App 仍需回环 WS，只保留一个必要的后台管理实现，集中所有权、启动竞争与就绪判断。
- 不自动把共享接入失败降级为另起独立写入后台，避免再次出现同一会话的 active writer 冲突。
- 实际 executable、连接端点、CODEX_HOME 与能力来自同一份解析结果；不按文件更新时间猜兼容性，不散落硬编码机器端口和路径。
- 代理策略留在外部代理启动器或显式环境中。项目内部不再保存第二套代理配置；回环连接绕过代理属于传输行为。

交付：平台/客户端能力表和选定方案。尚未证实的组合明确列缺口，不先承诺全平台等价。

### 3. 重写公共核心与平台适配

- 统一进程超时、取消、输出读取及回收；平台差异只处理实际需要的创建参数、服务和句柄行为。
- 分开后台准备、字节传输、RPC 配对与 Codex 事件处理；删除试验入口和重复的进程/PID管理。
- 微信使用一个协议实现，身份和重绑使用一个业务实现。错误详情既能定位失败阶段，也不回显凭据、请求正文或敏感 URL。
- 配置、默认值、依赖、命令目录、能力及展示字段各有单一来源。用户设置、Codex 实际状态与观察缓存不互相冒充。
- Linux 用系统服务能力，Windows 用其原生任务/进程能力；微信桥的自启与 Codex 后台管理分开。
- 保留小而明确的数据记录与持久化边界；不让各组件共享并任意修改整个 Bridge，也不为此引入通用状态机框架。
- 代码、用户数据、运行记录、日志、临时文件与安装产物明确分离；开发目录与安装目录复用相同启动逻辑。

交付：可替换的共同核心，两平台不再各自实现同一业务。

### 4. 重新实现交付、重绑与用户界面

必须保持的交付行为：

- 普通消息默认 steer，`/queue` 明确排队；准备/明确未提交可恢复，已提交或结果不确定不自动重发。
- 结果携带连接、后端、会话和轮次来源；重连和切换不能混入旧结果。
- 中途完整回复及时转发；最终回答、附件、切片及结束提示保持顺序和分组失败策略。
- 停止、重启、本地状态与帮助不被慢后台阻塞；审批与原生提问不能误当普通 prompt。
- 原生队列或历史核对只有在等价性成立时才替换本地实现，不凭字段存在宣称幂等或恰好一次。

绑定失效统一为：

1. 区分网络故障与确定的认证失效；认证失效后暂停微信收发和新的输入提交，不循环扫码。
2. 通过系统通知提醒并给出当前平台可直接运行的重绑命令，终端/日志保留同一指引；不依赖失效的微信通道发送提醒。
3. 同一次失效不反复弹通知。重启后仍能看见待重绑状态，通知失败不丢失该状态。
4. 已运行的 Agent 不因绑定失效被擅自终止；已产生的结果保留待处理。
5. 显式重绑时避免与运行中的收发竞争；同身份保留交付状态，换身份明确确认并隔离旧交付。提交顺序与未完成标记统一，失败不造成身份混用。

展示从旧版满意格式出发：状态、列表、指令提示、接收/结束提示与字段统一渲染；新增故障提示简短说明现状和下一步，不增加调试流水账。

### 5. 收口依赖、安装与数据迁移

- 先列真实能力需求，再选择平台实现。原生工具/API成熟可用时优先；不能为删一个小库而换成更重的脚本或脆弱实现。
- Linux 优先 `qrencode`；Windows 先核对已有原生工具/API，不能假定系统自带二维码编码能力。仅在缺少合适原生方案时保留必要回退，避免两平台无条件安装 `qrcode`。
- 网络、WebSocket 与媒体加密继续优先成熟实现；不自行重写分帧和密码算法。删除依赖以没有实际使用为依据。
- 安装继续遵守 INSTALLERS 约定：统一网络入口、交互菜单、无副作用 dry-run、初始化分离、集中依赖、保留数据、自启默认关闭和附加组件入口。
- 构建只验证程序可加载及必要能力，不扫码、不连接模型、不修改当前后台。候选版本不能满足现有配置时，激活前明确拒绝，不静默改变连接模式。
- 旧配置与状态做有界、明确的迁移；源码中的临时开关和过渡脚本不成为永久兼容层。
- 媒体快照、下载和日志规定清理边界，只清项目拥有的产物，不删除用户原文件。

交付：两平台一致的安装/运行心智模型，平台实现保留合理差异。

### 6. 验收、精简文档与收敛仓库

- 指定测试会话验收固定源码副本，先核对文档与版本；不可用时如实报告，不换代理或把静态检查称作测试通过。
- 离线重点覆盖交付结果未知、早到/迟到/重复事件、绑定失效与部分重绑、取消回收、后台归属、升级与旧状态迁移；不照抄新实现写自证测试。
- Linux 与原生 Windows 分别验证服务/任务、App/CLI共享、微信文字/图片/文件、中途回复、原生问题与审批、网络重连和重新绑定。离线模拟不能替代平台实机结果。
- 普通 Codex、App 内置后端和 codex-deepseek 分别记录实际覆盖；不能把一个成功扩大成全部支持。
- 文档只留入口、日常操作、架构边界与兼容依据；交接流水、临时清单与过时评审在吸收后移出活动文档。
- 分主题提交；核对私有库只含项目源码和可发布资料，不含账户、状态、代理私密信息或用户会话。
- 所需源码已留存、验收结果明确并成功推送后，删除 D 盘旧开发副本；不得删除仍被 Windows 入口引用的助手，先移除实际依赖。

## 预期收益与成本

收益是只维护一套微信身份/交付业务、一套 Codex 协议接入和少量平台适配；代理、后台与客户端不再互相接管职责。依赖、入口、配置和临时文件减少到可解释的范围，跨平台开发通过 Git 衔接。

主要成本是后台共享语义、崩溃与取消时序、旧数据兼容及 Windows 实机验收；模块重排本身不是难点。允许全部重写，但每阶段都必须能对照行为基线说明保留、替换和删除了什么。

完成时报告：删除的重复机制与依赖、入口/配置来源的变化、保留或取消的兼容路径、实际通过的测试与未验证组合；不以文件数或行数下降代替收益。
