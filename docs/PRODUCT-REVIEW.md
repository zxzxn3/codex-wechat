# 使用提示、设置与功能成本审视

2026-11-01。以当前源码为依据。复杂度和优先级是静态判断，不是压测、延迟实测或 API 账单。用户目前实际确认的是扫码、普通对话及图片接收；共享桌面、steering、文件收发及本轮测速仍待实用验证。

## 提示原则

用户需要知道：消息有没有到、接下来会不会影响当前工作、结果在哪里、失败后怎么办。

| 时机 | 提示设计 | 当前状态 |
| --- | --- | --- |
| 普通消息开始执行/追加成功 | 默认两段通道延迟，可用 /ack 自定义；空字符串关闭 | 已实现；发送延迟为本条估算，接收延迟为上次成功发信耗时 |
| 新建、恢复、切换会话或设置 | 会话摘要含动作、名称、模型/强度、目录；设置摘要含动作、模型、目录 | 已实现 |
| 连接桌面活动轮次 | 摘要后说明后续消息和 /stop 会影响同一个任务 | 本轮保留并简化 |
| /status | 运行状态、排队、审批、发送失败数，以及会话、模型、权限、协作、连接、模式、上下文、Token 和账户限额 | 按需查看 |
| /settings | 只列出处理提示和附件上限，不重复展示运行状态，也不建立另一套修改机制 | 本轮实现，只读 |
| 操作被拒绝 | 说明当前状态与下一步，例如“等待结束或 /stop 后再切换” | 已有，继续统一措辞 |
| 操作失败 | 区分未执行、已部分执行、结果不确定；不能只报“失败” | 已修正一部分，继续审视 |
| 下载/思考期间 | 不主动每秒推送进度 | 当前默认，减少消息噪声 |
| 已完成 | 正文和附件后可额外发送完成提示，仅成功轮次；空字符串关闭，当前默认关闭 | 本轮实现 |

“已收到/已入缓冲”“已投递当前轮次”“模型已读”“任务完成”是不同阶段。处理提示只代表程序开始处理或后端接受了追加，不保证模型已经读取，更不代表完成。不要把 shared daemon 的状态、当前轮次信息隐藏成笼统“在线”。

低频技术字段放在 /status；普通提示不打印 RPC 方法、token、命令输出或推理。失败时可以给脱敏技术原因帮助定位。/stop 的作用范围、部分失败和不确定投递等影响必须始终展示，不作为可关闭装饰。

## 设置：先集中已有的 7 项，再考虑 2 项

| 项 | 修改入口 | 生效范围 | 建议 |
| --- | --- | --- | --- |
| 后端 | /backend | 当前微信入口，记住各后端会话 | 保留 |
| 模型 | /model | 当前会话 | 保留；使用后端清单 |
| 思考强度 | /effort | 当前会话 | 保留；按模型校验 |
| 工作目录 | /cwd | 当前会话 | 保留；已有目录，不自动创建 |
| 工作中消息模式 | config.json inputMode | 网关重启后 | steer 默认，queue 留作高级选项；暂不增加指令 |
| 处理提示文本 | /ack text | 微信入口，跨重启保留 | 默认 `{发送延迟}/{接收延迟}ms`；空字符串关闭，不再另设开关 |
| 附件大小限制 | config.json media.maxMiB | 网关重启后 | 保留本地设置，避免变成远程上传权限调整 |
| 会话摘要详细程度 | 尚未实现 | 微信提示 | 可选候选；先试用简短默认值，确有需要再加 |
| 结果尾部耗时 | 尚未实现 | 最终回复 | 可选候选；/ping 仅显示微信通道，不显示 Agent 耗时 |

因此目前 /settings 只展示处理提示和附件上限；会话、模型、目录、模式等运行信息只在 /status 显示。没有实现万能 /set、任意 JSON 修改或新的配置存储。模型/强度/目录仍通过已有指令修改；运行时状态优先级以现有实现为准，不复制声明一份默认值。

更底层的 command/env、sharedDaemon、重试次数、CDN 地址、允许用户、文件路径边界、审批策略和状态目录，继续留在代码/本地高级配置或原 Codex 权限系统里。它们不是常用手机开关，有的会改变权限或连接身份。未来若要远程改，需逐项定义范围与恢复方式。

## /ping 的计量含义

命令不调用模型、不启动后端、不读取会话历史、不发额外网络探针。它只在正常发件箱排入一条合并回复。发件箱有旧消息或大附件时，该回复也会等待；当前简短格式不显示这段内部等待。

报告显示为一行“pong. 120/80ms”。`{发送延迟}` 使用本条入站估算，`{接收延迟}` 使用上一条成功发送样本，不附加解释段落。合并气泡在发出前无法知道自己未来的发送耗时，因此本次 ping 的发送耗时只供后续提示使用。缺少任一段数据时显示“-”。接收延迟为成功发送 API 请求耗时，包含请求/响应，不是手机下行单向耗时；测量边界留在文档。

不展示程序处理、排队、失败重试、历史中位数或 Agent 耗时。队列本身保持原有顺序，因此用户等待可能长于两段数字之和。若测速跨越重启，则明确计时失效。没有调用模型测提供商速度。

微信接口确认不等于手机已收到或渲染，因此这个数字不能称为“手机往返 RTT”。手机上从发出 /ping 到看到 pong 的等待，更接近体感完整延迟；若未来要自动精确测手机往返，需要手机端时间测量或收件回执能力，当前协议接口没有提供足够证据。

## 功能成本与复杂度

| 功能 | 运行成本 | 主要复杂度 | 取舍 |
| --- | --- | --- | --- |
| /help、/settings、状态摘要 | 文字回复；不调用模型 | 低：展示与真实状态一致 | 核心，集中提示模板 |
| /ping | 一条文字回复；统计只驻内存 | 低至中：时间来源、重试、重启边界 | 核心，按需测速 |
| 会话、模型、目录切换 | 本地 RPC、元数据与状态保存；无推理请求 | 中：有效设置、编号失效、失败不误报 | 核心 |
| steering | 输入 token 加入原轮次，可能改变后续工具工作量 | 高：轮次结束竞态、停止、明确拒绝与投递不确定 | 你的核心诉求，保留 queue 回退 |
| 桌面共享 | 连接/事件订阅本身不另起推理；新消息按轮次计费 | 很高：原请求所有者、事件订阅、断线和多客户端竞态 | 先验证，不继续叠加更多后台能力 |
| 图片/文件接收 | CDN、解密、磁盘；图片可能增加模型输入量 | 中高：大小、格式、地址、模型能力 | 核心，维持大小限制 |
| 文件回传 | 文件快照、加密、上传和发送；不需额外模型调用 | 中高：路径权限、重试、重复送达 | 保留路径边界，手动发送作补充 |
| 后端切换 | 新 proxy 连接及模型清单查询 | 中：home、会话和设置隔离 | 保留两个现成启动器，不复制认证 |
| 自启/重启 | 微信用户服务；需要时另起承载后台的临时用户服务 | 中：共享 daemon 与网关生命周期 | 自动就绪；已有后台优先复用，网关重启不结束桌面任务 |
| 持久队列/恢复 | 状态文件重写、fsync、媒体快照留存 | 中高：部分成功、重复/丢失、存储增长 | 优先可靠性，再据计量优化写入 |

这里的“无推理请求”不等于网络或平台服务没有任何成本。没有读取当前价表或账单，不给金额估算；已有任务的 token/工具成本也不会因输入方式叫 steer 就消失。

## 下一步的优先级

1. **先验证共享桌面接入与 steering。** 尤其是轮次完成竞态、桌面待审批、/stop 和连接恢复。现在已有离线用例，但用户要求不做操作测试，不能把实现当作验证。
2. **补断线后的结果补取。** 当前只转发在线订阅期间收到的结果，手机出门时更容易遇到网络切换；应按最后确认轮次恢复，并避免重复推送。价值高，复杂度也高。
3. **梳理共享模式的重启策略。** 现在 /restart 在有桌面活动轮次时拒绝。将来可支持只重连网关、保留桌面任务，但必须把未投递/投递中的消息恢复规则一起设计，不能简单删掉 busy 判断。
4. **让通道控制回复不被大附件长期挡住。** 当前同一发件箱顺序发送，/ping 也会排队；按用户要求简化后的两段数字不包含这段等待。可考虑控制回复优先级，但先定义文字说明与对应附件的顺序，避免乱序。
5. **统一命令注册和展示模板。** HELP、MANAGED 与 control 分支仍需分别维护，存在漏更新风险。可以用轻量命令表集中名称、用法、是否调用后端，不需要构建插件框架。
6. **优化重复元数据和格式说明。** 每张图可能查询 model/list；每次输入/steer 都带回传格式提示。可以按后端缓存清单、缩短说明或按线程管理，但需处理模型变化和上下文压缩，不能仅为少几个 token 牺牲可用性。
7. **明确媒体保留与失败记录重发。** 目前不自动删媒体，失败记录最多 20 条。适合先保守使用；未来再提供只操作过期且不被引用的文件的清理计划，以及由用户选择的失败重发，避免隐式重复执行。

本轮已实现：简短/详细提示分层、只读 /settings、/ping 与内存计时；按用户明确的使用目标，补上共享后台未运行时自动启动，并与微信网关分离生命周期。其余条目仍是待讨论建议。没有执行操作测试、启动/重启现有服务或清理操作。
