# 输入、交付与恢复边界

本文说明输入提交、会话切换、输出排队、发送确认和额度。连接所有权与并发准入见
[ARCHITECTURE](ARCHITECTURE.md)，配置和资源清理见 [CONFIGURATION](CONFIGURATION.md)，
日志与隐私见 [DIAGNOSTICS](DIAGNOSTICS.md)。

## 输入与会话切换

输入以一次保存从inbox进入currentInput。RPC前记dispatching，接受后记accepted；
preparing可恢复，dispatching结果未知、accepted均不自动重发。clientUserMessageId只是
追踪标识，未经验证不承诺服务端持久去重。明确不能steer可排队；超时/断连不算明确拒绝。
控制命令在入站保存时进入有界 `pendingControls`：入口在达到 `PENDING_CONTROL_LIMIT` 时拒绝新控制，
每条 lane 的内存队列也以同一值封顶；异常或恢复状态超出的控制会被丢弃并提示，而不是无界恢复。
尚未开始执行的条目重启后重新入队；
已经开始执行但进程中断的条目不盲目重放，恢复时提示用户重试。这样避免保存与内存队列之间的
静默丢失，同时不承诺跨进程恰好一次执行。换微信账号会丢弃旧账号尚未执行的控制项；同账号
重新绑定会让待执行媒体控制改用新的会话上下文。`/restart` 在确认服务重启前保留
`restarting` 状态，重启成功后由新进程清理；明确拒绝或操作错误会回复失败并正常清理控制项，
未处理的中断保留 `restarting`，下次启动提示可能未完成。

会话标题检索使用原生 `thread/list` 的 `searchTerm`；4–32 位会话 ID 前缀通过分页枚举
会话列表后本地匹配。两者都不解析 Agent 正文，也不调用模型。`/switch` 对唯一匹配直接
采用；多个结果只保存当前候选并要求编号选择，避免按模糊线索静默切错会话。

`/switch` 和 `/new` 允许在回合运行时执行：旧回合只在本地 detach，继续在后台运行但不再
交付；旧来源尚未发送的输出、当前输入和排队输入会作废，worker 收到合成的 discarded 结果
后退出本轮。已进入发送 API 的一条无法撤回。等待审批或原生提问的回合在被 detach 时不会作答，
它因此在服务端停到自己的超时为止，而不是继续跑完。`/model`、`/effort` 和 `/cwd` 使用
`thread/settings/update` 只修改后续回合；当前回合、当前输入和已在途输出都不受影响。
目标的读取、resume 或新会话创建在不可逆 discard 之前完成；目标准备失败时旧输入、输出和
当前回合保持不变。`/new` 在服务端已经创建线程后若本地提交失败，会尽力调用
`thread/delete` 删除这个新建的空 thread；`/switch` 只释放已有目标线程的订阅，绝不删除
用户原有会话。真实服务端的删除行为仍待平台验收。
`/backend`、`/compact`、`/restart` 和 `/settings shared` 仍要求空闲，因为它们会关闭连接、
修改当前会话或重启服务，不能保证旧回合静默继续。

## 输出与附件

每份结果固定携带来源、会话、轮次与目录；选择代次、连接代次不持久化。异步附件快照完成
后再核对来源。已入发件箱的内容不因切换重新解释。完整中途消息按原生item ID去重，
最终回答不再合并重复进度；当前不回放断线期间全部结果。
自动附件和显式 `/get` 共用同一 cwd 范围；解析符号链接后拒绝桥状态。桥的检查是保守近似，
不是 Codex sandbox 等价边界：桥不知道 agent 的 deny-read、permission profile 或外部
sandbox 规则，agent 被拒绝的 cwd 内文件仍可能在 OS 权限允许时被桥读取。敏感材料约束由
附件 skill 提示，但不构成强制隔离。

正文、附件和结束提示成组入队，切片与稳定消息ID固定。正文重试耗尽停止本组后续正文；
单附件失败可继续其它附件，但抑制结束提示。失败通知不递归，失败历史有界。
每条耗尽只增加一次连续失败数，成功发送与出队/清零同次保存。微信接受后本机保存前
崩溃仍可能重复送达，不承诺恰好一次。

## 发送确认与投递未知

发送是否成功以服务端返回的有效消息 id 为准：HTTP 200 且 ret=0、但响应不含非空的
msgid/msg_id/message_id/messageId/msgId 时判定为**投递未知**（WeChatNotAcknowledged），
不自动重试。首次出现即隔离当前条目并暂停整个出站队列；条目进入 failedOutbox，标记
`status=delivery_unknown`，计入连续发送失败；其余 outbox 保留。暂停是运行时状态，
重启后不会保留，但 outbox 本身仍持久化。这是**经验判据而非契约**：
协议文档的成功响应示例就是 `{"ret":0,"errmsg":""}`，字段表没有消息 id，官方维护者也说明
"ret=0 只代表 API 层接受、不保证投递"，契约本身无法区分投递与静默过滤（出处见
[SOURCES](SOURCES.md) 的"微信下行投递"一节）。该错误属于响应内容
而非请求本身，日志里体现为 output.delivery_unknown / output.failed 的
error_type=WeChatNotAcknowledged 与 error_code=服务端 ret，不计入 api_error_kind。
实测依据：某 bot 出站文本被服务端静默丢弃期间，sendtyping 和 getconfig 全程正常，
sendmessage 一律返回 {"ret":0} 且无 id；若把这种响应当成功，条目会离开发件箱而用户
收不到任何内容，只有 wechat.send_ack 的 status=no_id 留有痕迹。排查投递失败与本地过滤
时，先看该事件的 acked/no_id 计数。
output.failed 的 send_failures 保存当时连续发送失败条目数，成功清零规则不变。

**当前怀疑，不是已证实的契约**：`WeChatNotAcknowledged` 可能是账号开始进入短时限流或
静默丢弃阶段的首个可观测标志；它也可能来自单条消息过滤、接口异常或响应格式变化。单次
出现不足以判定封禁，必须结合同一账号随后多条正文/完成提示是否同时无 ID、认证是否仍有效、
入站是否仍正常，以及换账号或等待后是否恢复。这个怀疑只用于排查顺序，不能替代平台侧证据。

### 出站节流与静默丢弃后的处置

2026-11 之前的行为是每条失败固定 1s 连试 3 次，耗尽后无条件发一条失败通知。
实测下行被整体静默丢弃时，这一条回复会产生 6 次下行请求（原条目 3 次 + 通知 3 次），
而通知本身也必然被丢弃。现在的策略：

- 段间间隔：连续入队条目之间至少 `SEND_SPACING_SECONDS`（2.5s），切片后的长回答不再一次性
  突发；单个条目发送时不受影响。
- 传输失败退避：只有普通传输错误（`WeChatTransportError`、超时、连接失败和 `OSError`）
  按 `SEND_RETRY_SECONDS × 3^(n-1)`（1s、3s）重试；明确 API 拒绝和未知本地异常直接失败，
  不再重试。
- 未确认投递的特殊处置：`not_acknowledged` **首次出现即**暂停出站；当前条目立即隔离为
  `delivery_unknown`，不发失败通知，不自动重放。暂停只存在于运行时，当前 outbox 和
  暂停期间新增的输出都保留。下一次被接受的入站消息清除运行时暂停并刷新预算，sender
  按原顺序继续发送；如果用户先发 `/discard`，则先清空 pending outbox，再恢复。
  以 `output.delivery_unknown`、`output.send_paused` 和 `output.discarded` 记录。
- 可观测性：`delivery` 只回答"**现在**是否健康"——连续发送失败达到
  `DELIVERY_DEGRADED_THRESHOLD`（3）时为 `unconfirmed`，否则 `ok`。no-id 暂停本身不写
  `status`，因为它只是运行时状态；历史另由单调累计的
  `delivery_unknown`（曾发生多少次无 id）与有界的 `delivery_unknown_retained`（仍留在失败历史
  中的条数）表达。成功一次只清连续失败计数，不抹掉历史总量，也不让一次历史事件把
  `delivery` 永久钉在 `unconfirmed`。连续失败计数属于运行时状态，重启后归零。

发送间隔、传输失败退避和 no-id 暂停三项互不排斥；入站消息继续轮询。用户可用 `/discard`
主动清空 pending outbox；清空操作保留正在发送中的一条，并在清空后追加一条数量确认。

### 每条入站消息的回复额度

社区实测（[SOURCES](SOURCES.md) 有出处）每条入站消息约允许 10 条主动回复，超出返回 `ret:-2`，
官方未文档化。现在有显式预算：`sending.replyBudget` 默认 9、范围 **1–100**，按**服务端回话的次数**
计数（正文分段、处理回执、结束提示、附件；静默丢弃与明确拒绝也算，因为服务端处理了那次请求；
超时或连接失败这类根本没到达的请求不算），`/` 续传提示不计入，
作为第 10 条发出。默认值取在经验上限之内，上限 100 是留给知情者的逃生口：把额度调高会越过
平台的经验线，风险由改配置的人承担。

- 判据是"服务端有没有处理这次请求"而不是"用户有没有收到"：只按成功计数会在通道开始丢弃消息
  时让刹车变得最松（`used` 不涨、请求照发），而那正是最需要收手的时刻。代价是故障期交付条数
  可能少于额度值——一次抖动占掉一次额度，用户看到的段数会低于 `replyBudget`。
- 这个键**不进 `/settings` 面板，也不进 `/help settings`**（避免普通用户误调），但仍然可以改：
  编辑 config.json，或 `/settings budgets <整数>`（`sending.replyBudget` 是等价的长名）。
- 额度高于经验上限（9）时，启动或热加载会记一次
  `config.reply_budget_above_ceiling`（`budget`、`ceiling` 两个数值字段），值不变就不重复记；
  这样用户发来的日志能直接看出"被封可能是自己调高了额度"。
- 额度用尽时不再发正文，改为插入一条 `budgetNotice`，提供继续和清空待发队列的入口，然后等入站；
  该提示豁免预算检查，每个入站周期最多一条。
- 这条提示本身也是一次发送。若它拿不到回执（通道正在丢弃消息），按"不再叠加"处理：
  不派生失败通知、也不重新排队；它触发 no-id 暂停。下一条入站解除暂停，并按原顺序继续
  发送保留的旧队列。
- 任何被接受的入站消息（含 `/` 与任意命令）都会刷新额度：`refresh_reply_budget()` 递增
  `inboundSeq`、把已用条数清零并唤醒发送循环。普通额度耗尽时队列按原顺序继续；
  若存在 no-id 暂停，则解除暂停并按原顺序继续发送保留队列；用户也可以先 `/discard`
  主动清空。
- 已用条数与 `inboundSeq` 一起持久化，重启后不会被误当成"额度已刷新"；序号对不上时按新周期算。
- `/` 是 `/continue` 的别名，只出现在 `/help all`；它自己的处理函数不产生任何回复，
  避免"用 `/` 换一条 `/` 回执"的死循环。
- 这是**本地预算**，不是服务端承诺；它按经验值把每轮压在平台愿意接受的范围内。
