# 复杂度与取舍

以下是按职责边界的维护成本判断，不是工时预算或代码占比。能力范围见 [CAPABILITIES](CAPABILITIES.md)，运行契约见 [ARCHITECTURE](ARCHITECTURE.md)。

| 部分 | 成本 | 主要负担 |
| --- | --- | --- |
| 桌面活动会话共享 | 高 | 多客户端、早到/迟到事件、请求归属、轮次竞争、App内部接口变化 |
| 交付与重连 | 高 | 提交结果不确定、崩溃恢复、去重、输出顺序及部分失败 |
| 安装与更新 | 高 | 环境差异、版本构建、旧版清单、稳定入口和跨平台服务注册 |
| Windows托管 | 中高 | 计划任务、进程/Job Object、单实例、退出码、通知及实机验证 |
| 媒体收发 | 中高 | CDN、加解密、快照、大小限制、文件权限和部分失败 |
| 重绑与认证 | 中 | 扫码/服务并发、同号保留交付、换号隔离、半完成状态 |
| 原生问题/审批 | 中 | 实际接收连接与回答归属、桌面和微信的并发操作 |
| 命令、提示、切片和状态 | 低至中 | 主要复用原生协议、快照与纯函数；网络探测另有子进程 |

普通CLI和App共享大部分协议、连接和交付代码。App内置CLI发现与接入桌面正在使用的会话是两回事；后者承担更多状态边界。

- 单独去掉Linux App只能减少很薄的发现/入口代码；Windows App仍需要公共共享逻辑。
- 去掉Windows App可减少一部分内部接口维护，但若仍支持Windows CLI，托管、安装和进程层仍要保留。
- 去掉整个Windows平台、桌面活动会话共享或媒体能力才会明显减负，同时也有直接的功能损失。
- 单独去掉一个后端名称、短命令或模板变量，收益很小。

这些是后续取舍的依据，不代表已取消任何能力。重构优先解决已观察到的边界问题，避免为减少文件行数扩大改动。
