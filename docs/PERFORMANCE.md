# 发送延迟观察（历史采样）

2026-11-03 对 `logs/bridge.jsonl` 中带 curl 分段计时的成功请求做了聚合；这是本机
Linux 观测，不是 Windows 或微信显示延迟的保证，也不是当前版本的固定性能承诺。

| 请求 | 样本 | 平均总耗时 | curl 总耗时 | 桥接额外 | 等待首响应 | TLS/隧道 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `sendmessage` | 403 | 494.2ms | 486.0ms | 8.1ms | 337.2ms | 145.2ms |
| `sendtyping` | 628 | 255.5ms | 247.9ms | 7.6ms | 97.8ms | 145.8ms |

同一批 `sendmessage` 的 p50 为 489.2ms、p90 为 539.5ms、p99 为 671.1ms。

结论：

- 延迟主要发生在微信 API 的网络路径：每次请求重新建立 TLS，再等待服务端首响应。
  现有数据不支持“Python 交付循环是主要瓶颈”的判断。
- 采样版本每个微信请求启动一次 curl，桥接额外开销约 8ms；Windows 进程成本未测。
  当前 API 已改为常驻异步 libcurl 池，收信与发送分池，空闲 60s 释放；实际收益待运行验证，
  可用日志 connection_reused 对比新建与复用请求。媒体传输复用 outgoing 池；/ping 仍使用 curl 子进程。
- 采样版本的 typing 在接收提示之前等待 `getconfig` / `sendtyping`，会额外拖慢提示。
  当前已改为后台并行执行，输入准备和提交不再等待 typing 网络请求；效果尚待运行验证。
- 已观察到旧实现将 10s 收信等待超时当作故障，再退避 2–5s，造成额外收信空窗。
  当前默认等待改为 35s 加 5s 余量，明确处于等待响应阶段的收信超时直接重轮询；
  连接/TLS/部分响应超时仍保留故障处理，不将所有超时视为空结果。
- 接收提示在消息真正发送前生成，`{egress_ms}` 只能表示最近一次成功发送的通道耗时，
  不是当前回复的发送耗时，也不包含模型生成、排队和附件准备。最近样本会跨服务重启保留；
  从未成功发送过时仍显示 `-`。

未覆盖：Windows 实机、App 内网络路径、不同代理/VPN 条件。缩减超时不能降低正常请求的
网络耗时；本次连接池改动尚未采集优化后的真实微信样本。

## 暂不实施的恢复增强

- 限流专用退避：遇到确认的服务端限流时延长等待。已观察到发送返回 -2，但尚未确认是限流。
  现在已有段间 2.5s 间隔、传输错误的 1s/3s 指数退避，以及未确认投递首次出现后的运行时
  出站暂停；下一条普通入站恢复发送，积压按原顺序保留；显式 `/discard` 会在恢复前清空积压。
  两者都不再自动隔离或丢弃积压。仍不引入"识别到限流码就特殊延长"，
  因为没有证据说明 -2 就是限流，出现证据后再核对错误分类。
- 连续连接故障后重建连接池：仅在普通重连仍不能恢复时考虑。Hermes 的相关处理针对
  aiohttp 与部分代理的资源问题，不能直接推断本项目的 libcurl 也需要。目前未见实施必要。
  将来若实施，只处理故障池，不打断其它请求，也不自动重放提交结果未知的消息。
